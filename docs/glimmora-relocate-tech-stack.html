01 — How to use this documentA note for two audiences.

For the designer
You can share this document with backend engineering as the starting point for the stack conversation. The SOW already commits the platform to FastAPI + PostgreSQL + React + LLM orchestration + Knowledge Graph. This document fills in the complements needed to make that stack actually work at enterprise scale — a workflow engine, payments, auth, observability, infra, and so on.

Each section proposes a default with plain-language rationale, then flags the decisions that the backend team needs to confirm. You do not need to defend every choice — just present the document as "this is our current thinking; tell us what you'd change" and let the backend team take ownership of the technical commitments.

Legend

02 — Project contextFor engineers reading this document cold.

Glimmora Relocate is an AGI-native cross-border relocation platform. Six portals (Consumer, Employer, Partner, Corporate, Admin, Public) orchestrated by an AI Copilot that reasons over a Country Knowledge Graph and per-user Digital Twins.

For full scope, read the reference documents in this order:

  • handbook.html — plain-language overview (25 min read).
  • architecture.html — reference architecture, data model, flows, roadmap.
  • portal-flows.html — per-portal IA and user flows.
  • mapping.html — personas × portals × roles matrix.
  • SOW (source of truth) — /Users/kavi/Downloads/Glimnmora Relocate_SOW.docx.

What makes this stack non-standard

  • AGI Copilot is the primary UX, not a sidebar. LLM orchestration is a first-class layer, not an add-on.
  • Long-running workflows. A single user’s relocation plan can execute over 6–12 months with dozens of dependent tasks. Durable workflow orchestration is mandatory, not optional.
  • Escrow-mediated marketplace. Money is held between user and partner; release is conditional on fulfilment. Not a standard e-commerce checkout.
  • Multi-tenant B2B (Corporate) sits alongside multi-consumer B2C. The stack needs to support both without forking.
  • GDPR + regional data residency. A European user’s twin, documents, and events should be storable in-region. Designed-in, not bolted on.
  • Partner + employer verification (KYB / KYC) is a prerequisite for transacting, not a post-facto check.

05 — FrontendThe six portals, one codebase.

Design owns this layer. The proposal below reflects what will make the designer’s life (and AI-assisted frontend work) most productive while staying aligned with what backend needs to integrate against.

Frontend framework · Next.js + React + TypeScript

Propose
Choice
Next.js 14+React 18TypeScript
Why
Next.js gives SSR for the SEO-critical Public Site and React Server Components for heavy data-driven screens. One framework serves all six portals — Consumer App, Employer, Partner, Corporate, Admin, Public — with per-portal route groups. TypeScript because we will share types with the backend via generated OpenAPI clients.
Alternatives
Remix (smaller ecosystem); Vite SPA (loses SSR); Astro (wrong tool for app-heavy portals).
For backend
Generate TypeScript clients from FastAPI’s OpenAPI spec. One command (openapi-typescript) keeps types synced end-to-end.

Design system & styling · Tailwind + shadcn/ui

Propose
Choice
Tailwind CSSshadcn/uiRadix primitives
Why
Tailwind + shadcn gives fast iteration and accessible primitives. Design owns the token layer (colors, spacing, typography) in a Tailwind config — the same tokens flow to every portal so the system feels consistent.
Mobile
The Consumer App ships as responsive web first, then a PWA (installable, offline-capable for documents). Native iOS/Android is a later wave when it earns its complexity.

State & data · TanStack Query + Zustand

Propose
Choice
TanStack QueryZustand
Why
Server state (lists, details, mutations) goes through TanStack Query — caching, retries, optimistic updates out of the box. Client-only state (UI toggles, in-progress form state) uses Zustand. No Redux.
Copilot streaming
Copilot turns stream from the backend via Server-Sent Events (SSE) — simpler than WebSocket and fits FastAPI cleanly. Frontend maintains a streaming-message component that updates token by token.
What Design commits to deliver for backend integration:
  1. A working Figma design system with components matching the shadcn set (so frontend can implement 1:1).
  2. A Storybook of built components per portal (eventually).
  3. Design tokens exported as JSON for Tailwind config.
  4. One Figma prototype per portal demonstrating the full user flow before backend builds the API for that flow.

06 — Backend & APIWhere most of the platform lives.

Language & framework · FastAPI on Python 3.12

SOW
Choice
FastAPIPython 3.12Pydantic v2SQLAlchemy 2.0 / SQLModelAlembic
Why
Locked by SOW §23. Python is also where the AI/ML ecosystem lives — same language for API handlers, LLM orchestration, and any ML workloads means fewer seams.
Async everywhere
FastAPI routes are async; database calls go through SQLAlchemy’s async engine or async drivers. LLM calls and external integrations naturally want async.

Architectural style · Modular monolith (at W0)

Decide
Proposal
Start as a modular monolith with clear internal boundaries (domain modules: auth, copilot, jobs, relocation, payments, trust, kg, workflow). Deploy as one service. Extract to microservices only when a seam becomes load-bearing — typically payments, workflow, or LLM orchestration.
Why not microservices day one
The team is small; user flows cross domain boundaries; we don’t yet know where the real load or team lines are. A clean monolith with real module boundaries is faster to build and trivial to split later.
Backend decides
Where the first seam should be. Common candidates: a separate LLM service (different scaling profile, different ops), a separate workflow worker pool (Temporal already gives this).
Decision for backend team. Confirm the modular-monolith starting point, or propose a specific service split for W0 with reasoning.

API style · REST + SSE (streaming)

Propose
Choice
REST (JSON over HTTPS)SSE for CopilotOpenAPI 3.1 contracts
Why REST
The full stack is straightforward CRUD over well-defined resources — jobs, applications, bookings, payments, documents. REST keeps the contract obvious, OpenAPI-documentable, and typed end-to-end.
Why not GraphQL
No client with radically different data needs. Six portals with similar queries don’t justify the GQL overhead.
Streaming
Copilot responses stream token-by-token via Server-Sent Events. Simpler than WebSockets; one-way (server → client) fits the shape of LLM output.
Webhook endpoints
For Stripe, KYC, ATS integrations. Signed and idempotent.

Multi-tenancy · Row-level (B2C + Corporate)

Decide
Proposal
Row-level multi-tenancy with a tenant_id on every domain row, enforced at the ORM layer and/or via Postgres RLS (Row-Level Security). Individual B2C users are their own tenant; Corporate accounts have many users under one tenant.
Alternative
Schema-per-tenant — stronger isolation but operationally heavy at B2C volumes.
Decision for backend team. Row-level with RLS, ORM-layer enforcement, or hybrid. Affects all query paths and auth middleware.

07 — Data layerPostgres first, with purpose-built stores for specific needs.

Primary database · PostgreSQL 16

SOW
Choice
PostgreSQL 16Amazon RDS / Aurora or Supabase or Neon
Why
SOW-specified. Handles users, jobs, bookings, payments, tasks, audit logs. With pgvector it also handles embeddings for RAG.
Partitioning / scale
Events and audit logs will partition by month once volume requires it. Read replicas for reporting; primary for writes.

Vector store · pgvector (in Postgres)

Propose
Choice
pgvector extension in the primary Postgres
Why
Fewer moving parts. The same database holds the documents and the embeddings; one SQL query can retrieve both a fact and its source row. Switch to Pinecone/Weaviate only if we prove retrieval latency or scale justifies it.

Knowledge graph · Neo4j (or PG + AGE)

Decide
Option A
Neo4j (self-hosted or Aura) — purpose-built graph database with mature traversal performance and tooling. The right tool if KG queries become complex.
Option B
Postgres + Apache AGE — graph extension on top of the primary DB. Fewer systems, weaker tooling, acceptable if the KG stays medium-sized.
Option C (start)
Model the KG as Postgres tables in W0/W1 — triples pattern (subject, relation, object, confidence, source) — and promote to Neo4j once traversal queries appear.
Decision for backend team. Recommendation is Option C at W0, with explicit commit to Neo4j (Option A) by W2 when the Country Knowledge Graph starts driving Copilot reasoning at scale. Confirm or counter-propose.

Object storage · S3 (or equivalent)

Propose
Choice
AWS S3 with KMS for encryption
Why
Documents vault (passports, degrees, visa forms, contracts) needs encrypted object storage with fine-grained access, versioning, and region-pinning for GDPR residency.
Field encryption
Sensitive fields get an additional envelope encryption layer with user-scoped keys for defense-in-depth.

Cache / pub-sub · Redis

Propose
Choice
Redis (ElastiCache or Upstash)
Why
Session store, rate limiting, Copilot short-term memory between turns, light pub/sub for in-process events.

08 — AI & LLM orchestrationThe Copilot stack.

The Copilot is the product’s main interface. Its quality depends less on the model and more on the retrieval, tool use, and guardrails built around it.

LLM provider · Anthropic Claude (primary)

Propose
Primary
Anthropic Claude — Opus 4.x for complex reasoning (plan generation, financial simulation explanation), Sonnet 4.x for conversation, Haiku for quick utility tasks.
Abstraction
All LLM calls go through a provider interface. We never import Anthropic’s SDK directly from business logic. This lets us add OpenAI / Gemini / self-hosted fallbacks without touching callers.
Prompt caching
Critical for cost. The Country Knowledge Graph subset + user twin snapshot are long prefixes — cache them on every Copilot turn.
Tool use
The Copilot calls defined tools: get_user_twin, search_jobs, simulate_financials, generate_plan, book_service, validate_document, etc. Tool schemas are shared with the OpenAPI spec.
Decision for backend team. Commit to a primary provider for launch (Anthropic recommended), plus a policy on fallbacks and data-residency implications of the provider choice.

Retrieval · RAG over Twin + KG + docs

Propose
Sources
(1) User Digital Twin state; (2) Country Knowledge Graph facts relevant to the user’s corridor; (3) vectorised document snippets (e.g. visa rules, tax guides); (4) flywheel-learned statistics.
Ranking
A domain-aware ranker combines semantic similarity (pgvector) with relevance features (country match, recency, source trust score).
Grounding
Every Copilot statement cites the source(s) retrieved. A response without citations is a bug.

Evals & guardrails

Propose
Evals
A versioned eval set per Copilot capability (job match explanation, financial simulation, document validation reasoning). Every prompt / model / tool change runs the suite in CI.
Guardrails
Output validators: schema validation on structured outputs; refusal for out-of-scope questions; PII detection; jurisdiction-sensitive content filters.
Observability
Every Copilot turn logs: user input, retrieved context, tools called, model + prompt version, token usage, response, any refusals. Traced end-to-end.

09 — Workflow orchestrationFor plans that live for months.

Workflow engine · Temporal

Propose
Choice
Temporal (self-hosted OSS or Temporal Cloud)
Why
A relocation plan is a multi-month workflow with dozens of tasks, human waits, retries, and timer-driven alerts (document expiry, visa deadlines). Temporal provides durable execution — the workflow survives deploys, restarts, and infrastructure churn. Celery / simple queues cannot do this well.
What runs in Temporal
Every long-running flow: relocation plan execution, document expiry monitoring, escrow state machines, KYC callbacks, scheduled flywheel jobs.
Alternatives considered
Celery + outbox — possible but we’d rebuild 30% of Temporal. AWS Step Functions — locks us to AWS; weaker local dev. Inngest — newer, less proven at enterprise scale.
Decision for backend team. Self-hosted Temporal (more control, more ops) vs Temporal Cloud (managed, straightforward cost). Recommendation: Temporal Cloud until volume justifies self-hosting.

10 — Payments & escrowThe most regulated piece of the stack.

Payments · Stripe + Stripe Connect

Propose
Subscriptions
Stripe Billing — $100/yr base, premium tiers, corporate seat licenses.
Escrow
Stripe Connect with separate charges and transfers — funds held on platform, released to partner on fulfilment confirmation.
Multi-currency
Users pay in their local currency; partners receive in theirs. Stripe handles FX; we surface the spread transparently.
Tax
Stripe Tax for VAT / GST / sales tax compliance.
Regulatory
Escrow licensing varies per jurisdiction — Stripe Connect handles much of this via its Connect account model, but we need legal confirmation per launch country.
Decision for backend team. Stripe Connect model: Standard (partner onboards with Stripe directly, simpler for us), Express (branded flow, more control), or Custom (full control, most compliance burden). Recommendation: Express.

11 — Auth & identityWho signs in, and are they who they say.

Auth · Clerk or Auth0

Decide
Needs
Email/password + passwordless + social; SSO/SAML for Corporate; MFA for Admin Console; session management; organisation model (Corporate accounts with multiple users).
Option A
Clerk — great DX, fast to integrate, organisations built in, reasonable cost at scale.
Option B
Auth0 — enterprise-grade, better for complex SSO requirements, higher cost.
Option C
Supabase Auth or self-hosted Keycloak — cheaper, more ops burden.
Decision for backend team. Pick one. Recommendation: Clerk for W0–W4 velocity; reassess at W5 if enterprise SSO requirements explode.

KYC & KYB · Persona / Onfido / Sumsub

Decide
User KYC
Light-touch for B2C consumers; heavier for premium + corporate.
Partner KYB
Business registration, licence documents, beneficial owner checks, sanctions screening. Non-negotiable before any partner can list.
Employer verification
Lighter than partner KYB but verified before jobs can be posted.
Decision for backend team. One vendor for user + partner + employer, or best-of-breed. Recommendation: Persona for its workflow flexibility (you can script different verification flows per entity type).

12 — Observability, security, complianceHow we know the platform is healthy and safe.

Observability · OpenTelemetry + Datadog (or Honeycomb)

Propose
Traces
OpenTelemetry end-to-end. A single Copilot turn traces from the frontend click, through FastAPI, through tool calls, through the LLM provider, back through database queries, and out to the user.
Logs
Structured JSON; every log line carries trace + tenant + user context.
Metrics
Business metrics alongside infra: time-to-first-token, tool-call success rate, escrow release latency, trust score distribution.
Error tracking
Sentry for both frontend and backend exceptions.

Security posture

NFR
  • Least privilege across IAM and DB roles; no shared secrets outside of a vault (AWS Secrets Manager or Doppler).
  • Encryption at rest via KMS for DB, S3, backups; TLS 1.3 everywhere in flight.
  • Field-level encryption for PII and financial data in the DB.
  • Audit logs for every trust-critical action; append-only, retained per policy.
  • Dependency + container scanning in CI (Snyk, Dependabot, Trivy).
  • Pen test cadence — annual external at minimum; scoped per launch corridor.
  • SOC2 readiness — designed in from W0; certification pursued at W5+ when enterprise deals require it.

GDPR tooling

NFR
  • Consent management surface in the Consumer App; granular consent per processor.
  • DSAR endpoint: machine-generated export of all user data on request.
  • Right-to-be-forgotten: soft-delete with cryptographic erase of user-scoped encryption keys, hard-delete on retention expiry.
  • Sub-processor register kept up to date as vendors are added.

13 — Infrastructure & deliveryHow it runs and how it ships.

Cloud · AWS (proposed) or GCP

Decide
Proposal
AWS — breadth of services, KMS, SES, RDS/Aurora, ECS, S3, multi-region maturity.
Alternative
GCP — stronger AI tooling (Vertex), cleaner BigQuery for warehousing. Viable if the team is more AI-native.
Decision for backend team. Cloud choice locks a lot of other decisions. Recommendation: AWS.

Runtime · ECS Fargate (simpler) or EKS

Decide
Proposal
ECS Fargate at W0 — serverless containers, no cluster ops. Migrate to EKS / Kubernetes when complexity / scale demands it.
Why not K8s now
The team is small; we do not need the control; the ops burden is high. Two services are much easier on Fargate than on EKS.
Decision for backend team. Confirm Fargate start, or argue for K8s from day one.

Infrastructure as code · Terraform

Propose
Choice
Terraform with remote state (S3 + DynamoDB lock, or Terraform Cloud)
Why
Multi-cloud portable, huge ecosystem, standard. Pulumi is viable if the team prefers TypeScript but Terraform is the safer default.

CDN / edge · Cloudflare

Propose
Choice
Cloudflare — CDN, WAF, bot protection, DDoS
Why
The Public Site is a high-traffic SEO surface and the Consumer App is global. Cloudflare’s edge network + security posture is the right default.

CI/CD · GitHub Actions

Propose
Choice
GitHub Actions; preview deploys via Vercel (frontend) + ECS review environments (backend)
Practices
Trunk-based development; required reviews; automated tests + evals in every PR; semver-tagged container images; zero-downtime deploys.

16 — The handoff packageWhat design sends, what backend returns.

What Design is handing over

  1. This document (tech-stack.html).
  2. The architecture document (architecture.html).
  3. The handbook (handbook.html) for new-hire onboarding.
  4. The portal flows (portal-flows.html) — IA, user flows, journey map.
  5. The mapping document (mapping.html) — personas × portals × roles.
  6. The SOW itself (Glimnmora Relocate_SOW.docx) — contract source of truth.
  7. Figma files: design system, per-portal prototypes (delivered wave by wave).

What we need back from Backend

  1. Written responses to the ten open decisions in section 15.
  2. A target repository structure (monorepo layout proposal).
  3. An initial OpenAPI skeleton for W0 (auth + user + twin endpoints) so frontend can generate TypeScript clients and start building against mocks.
  4. A development-environment runbook: how to stand up the stack locally, seed the KG, seed a test user, run evals.
  5. A first-pass estimate of W0 scope in weeks, with explicit dependencies and risks.

Working cadence proposal

  • Weekly design ↔ backend sync during W0–W2 while contracts stabilise.
  • Design leads the portal UX; backend reviews for API feasibility before designs are finalised.
  • Backend owns the API contract; design consumes via generated types. No hand-coded types on the frontend.
  • Figma + OpenAPI are the two sources of truth — one for what the user sees, one for what the server promises.
The posture of this handoff. Nothing in this document is written in stone. It represents design’s best synthesis of the SOW, the reference architecture, and current industry defaults. Backend engineers are expected to push back, substitute, and refine — and whatever the final stack looks like, it will have their name on it, not ours.
